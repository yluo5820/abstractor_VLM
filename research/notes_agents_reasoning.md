# Low-compute VLM projects: GUI reliability and temporal reasoning

Research cutoff: 14 September 2026. These are proposals and planning estimates, not measured experimental results. Reviewed selected methods/construction/evaluation sections of 18 primary papers, recorded in `sources_agents_reasoning.json`. This is not a claim to have read every page of those papers. ## Recommendation

A class project should run an inference-only diagnostic and a small, falsifiable intervention, then consider training only if a two-day pilot establishes a real failure. In this slice of the field, generic ideas are heavily occupied. I would rank the narrowly defined GUI retry project above the video fallback below, but assign only **medium novelty confidence** pending a fresh exact-topic audit and inspection of released benchmark examples. The novelty lies in the controlled question and measured decision consequence, not in inventing verification, abstention, counterfactual pairs, or active visual search.

## Candidate A: When is it safe to retry? Separating action failure from visual stasis

**Question.** Does a VLM's inference that an action failed track the action's actual effect, or simply whether the screen changed? Can a cheap observation-sufficiency check reduce duplicate actions without increasing missed failures?

**Concrete example.** A local mock interface records a note after an Add click, but leaves the currently visible view unchanged until the history panel is opened. In a matched failure case, the request is dropped and the visible view is also unchanged. Retrying in the first case produces a duplicate; retrying in the second case is appropriate. Conversely, an animation or toast can change the screenshot despite a failed write. Use benign local note, bookmark, list-item and settings examples, with task state logged by the test application.

**Contribution beyond closest work.** VeriGUI explicitly creates failure examples by reusing the previous screenshot and uses pseudo-online transitions in which incorrect actions return unchanged screens. VisCritic models action success from before/after visual differences. Neither makes a balanced success × visible-change factorial design the central evaluation. However, **Interactive Reward Agent (IRA) already actively checks hidden state and artifacts**, including a successful edit whose screenshot did not refresh. Therefore this proposal must focus on **the sequential retry decision, duplicate-action cost, and observationally indistinguishable outcome pairs**, not claim that active verification or hidden state inspection is new. GUI-RobustEval already evaluates error horizons; do not claim the first delayed-error benchmark.

Primary references: [VeriGUI](https://arxiv.org/abs/2604.05477), [VisCritic](https://arxiv.org/abs/2606.24525), [IRA / GUI-RewardBench](https://arxiv.org/abs/2607.25904), [GUI-RobustEval](https://arxiv.org/abs/2605.29447), [Task-State Representation](https://arxiv.org/abs/2607.00502).

**Dataset.** Build 200–300 independent local episodes, with 4 matched variants per episode: success/change, success/no-change, failure/change, failure/no-change. Include action classes that are idempotent (setting a toggle to a specified value) and non-idempotent (append a note). Labels come from application event/state logs. Use a subset of genuinely identical screenshots plus identical action histories for which success cannot be inferred from available evidence; explicitly grade these as needing observation, not as ordinary binary questions. Split by UI template and action family. Hold out at least one naturally behaving local application or real replay subset as an ecological check; synthesized HTML alone is weak publication evidence.

**Intervention.** A fixed policy classifies evidence as sufficient/insufficient and predicts whether retry is idempotent. On insufficient non-idempotent cases, acquire at most one or two read-only observations before deciding. Compare an always-inspect policy and the IRA-style evidence hierarchy at identical access and cost budgets. The first version is prompted and deterministic; optional later calibration is a logistic head on frozen features, not VLM RL. Do not give the method privileged state logs; these are evaluator-only. A DOM/API baseline is useful, but giving it hidden success flags would make the test trivial.

**Baselines.** Qwen2.5-VL-3B or Qwen3-VL-4B plus one 7–8B model; add a second model family for the full study. Use: direct screenshot judgment; expected-effect prompt; pixel/feature-difference rule; available VeriGUI/VisCritic checkpoints if released and compatible; always retry; never retry; always verify; IRA-style verifier under same observation budget. Existing checkpoint availability still needs to be checked before promising exact reproduction.

**Metrics.** Macro success/failure/insufficient-evidence accuracy; false-success and false-failure by factorial cell; duplicate-write rate; final task success after a maximum of two extra decisions; read-only observations per episode; risk versus observation cost. Report paired bootstrap CIs over independent source episodes, not treating the four variants as independent samples. Report image-only impossibility cases separately from cases containing subtle visual evidence. The relevant practical outcome is fewer duplicate writes at matched completion rate and observation budget.

**48-hour pilot.** 40 source episodes × 4 variants = 160 probes. Two small models × 3 policies gives 960 base decisions, plus at most 320–640 observation-followup decisions. Plan 1,300–1,600 total short calls, 2–4 images each, max 96 output tokens. First half-day: deterministic environment and labels; next half-day: validate 20 episodes manually; day two: inference and error taxonomy. Keep if two models show a consistent ≥15 percentage-point error difference attributable to change/stasis, and an observation gate reduces duplicate actions by ≥30% relative (and ≥5 points absolute where baseline permits) with task success within 3 points of always-inspect at ≤60% of its observation calls. These are proposed go/no-go thresholds, not statistical guarantees on n=40.

**Kill or reframe.** Stop the method claim if a simple expected-effect prompt or always-inspect policy achieves the same tradeoff, if failures only occur on impossible identical-image cases, or if IRA/another released benchmark already supplies this exact factorial/retry evaluation. Keep an honest replication-plus-counterexample project if course scope permits. Do not scale a toy benchmark to thousands of copies to manufacture significance.

**Compute planning.** Pilot 4–10 single-GPU hours. Full 200–300 source episodes, 3 models, 3–4 main policies, roughly 10k–18k short calls: plan **32–80 GPU-hours total**, spread over independent resumable batches; no simultaneous multi-GPU allocation needed. Prefer one 24–48GB GPU for 3–4B short-context inference; an 8B BF16 setup may need 48GB at the chosen image budget, or separately report a quantized configuration. This is a forecast; measure 100 calls on the actual cluster first. Human/UI engineering effort, not GPU time, is the main risk.

## Candidate B: Which missing frame is worth buying? Active evidence acquisition after visual uncertainty

**Question.** Given the exact same sparse video evidence, can a model identify which additional timestamp would resolve the answer, rather than merely refusing or guessing? Does targeted acquisition beat standard samplers under a fixed number of frames and calls?

**Novelty boundary.** **VirtueBench already labels answerability by frame sampling level**, and TRAPSBench already supplies paired answerable/unanswerable physical scenes. SynFlash/InfoShot already improve rare-event capture, Low-Frequency Trap already distinguishes final counting from trace recovery, and VideoAgent already does active video search. The remaining narrow delta is **one-step information acquisition quality conditional on a controlled ambiguous observation**, measured by the smallest discriminating evidence set and risk reduction per extra frame. Novelty confidence is **medium-low**; a generic uncertainty-aware sampler is not sufficient.

Primary references: [VirtueBench](https://arxiv.org/abs/2603.07071), [TRAPSBench](https://arxiv.org/abs/2608.13167), [InfoShot / SynFlash](https://arxiv.org/abs/2603.17374), [Low-Frequency Trap](https://arxiv.org/abs/2608.06361), [VideoAgent](https://arxiv.org/abs/2403.10517) (title-screened here; needs full method review before project commitment).

**Design.** Use 6–20-second clips with 2–6 selected frames initially. Form controlled video pairs that are identical at those observed timestamps but differ in event order or count in a narrow missing interval. Provide four candidate timestamp locations without revealing their images; the model may answer, abstain, or select one timestamp to inspect. After one reveal it answers again. Include (a) cases resolved by one reveal, (b) cases requiring two, (c) cases no permitted reveal can resolve. A finite candidate-video family allows exact computation of the discriminating timestamp; this is a certificate relative to that family, not a guarantee about unrestricted real-world videos. Use natural short clips and event annotations for an external validation slice. Avoid generated diffusion videos: CPU renderer plus existing footage suffices.

**Method and comparisons.** Direct answer/abstain; explicit uncertainty prompt; random extra frame; temporal midpoint; uniform doubled sampling; motion/feature-change sampler; InfoShot where applicable; VLM-selected next frame; a simple disagreement-based selector over plausible event hypotheses. Every method gets the same initial evidence and the same extra frame/call budget. Do not compare a one-call baseline against unlimited adaptive search. Separate hypothesis generation errors from selection errors using an oracle candidate-set ablation.

**Metrics.** First-step answerability and risk/coverage, selection of a discriminating timestamp, post-reveal accuracy, unnecessary-query rate, uncertainty persistence on irreducible cases, total pixels/tokens/calls/latency. Report accuracy conditional on evidence availability and paired performance on both members, so guessing one answer cannot hide missing evidence.

**48-hour pilot.** 50 paired scenarios = 100 clips. Two 3–4B models, 4 selectors and at most one reveal; ≤1,600 model calls. Keep if oracle one-frame acquisition improves accuracy ≥20 points, the learned/prompted selector beats midpoint and a feature-change sampler by ≥10 points at equal cost in both models, and the effect survives a non-rendered external slice. Kill the method claim if a midpoint/cheap sampler is within 3 points, if the model cannot answer even with oracle evidence, or if the improvement is explained by more calls/pixels. With only n=50, these thresholds select an experiment to scale rather than establish a paper result.

**Compute planning.** Pilot **6–16 GPU-hours**; full 200–400 short clips, 3 models and 4 budget-matched selectors: **24–72 GPU-hours**, 4–12 frames per call and short answers. Actual throughput must be measured; do not promise real-time performance from parameter count or GPU fit. Batches are checkpointable and independently restartable. Main practical risk is annotation and ensuring the answer really becomes identifiable.

## Candidate C (lower-priority backup): Update a visual fact; invalidate every conclusion that depended on it

**Question.** After a screenshot changes one underlying fact, does memory update the explicit fact but retain an invalid derived answer, such as a count, comparison, or selected item?

**Narrow delta.** WorldMemArena evaluates visual updates and memory lifecycle; MemLens evaluates updates and arithmetic reasoning. A potential new controlled angle is **transitive invalidation of derived visual conclusions**, rather than replacement of the same attribute. Example: a small seating chart supports “table A has the most empty seats”; a later partial screenshot changes one table, and the assistant must invalidate/recompute the ranking while retaining unaffected facts. Existing graph-memory and truth-maintenance research may already cover the algorithm. Treat this as an evaluation-led project, not a novel general graph-memory method.

**Experiment.** 150–300 short sequences of 3–6 diagram/UI snapshots with deterministic hidden state; fixed 256-token memory budget. Cross relevant versus irrelevant update with visible versus occluded dependency. Compare append-only summary, last-write-wins records, full refresh, and provenance-linked records that invalidate derived claims when their evidence changes. Keep shared frozen visual extraction and oracle-extraction ablations to distinguish perception from memory failure. Evaluate obsolete-derived-answer rate, preserved-unaffected-fact accuracy, recomputation cost and final accuracy. Split by relation/composition template; use a small real diagram or GUI transfer slice.

**Pilot / kill.** 30 sequences, two small models, four memory policies. Keep only if primitive facts update accurately while derived conclusions remain stale in ≥20% of relevant-update cases, and dependency invalidation halves that stale-conclusion rate without losing >3 points on irrelevant-update controls. Kill if standard last-write-wins plus recomputation matches it at the same token/call budget, or if WorldMemArena examples already implement this same transitive update diagnostic. **2–6 GPU-hours pilot; 16–48 GPU-hours full**, with cacheable image extraction. Novelty confidence low-to-medium; strongest as a backup if GUI setup proves cumbersome.

## Explicitly rejected broad pitches

- “Recheck the screen before clicking”: PUSV/TOCTOU (2604.18860) and pixels-versus-structure consistency gates (2607.04334).
- “Compare before/after screenshots to verify progress”: VeriGUI, VisCritic and Task-State Representation.
- “Use tools to verify hidden GUI state”: IRA already does this, with efficient tool selection.
- “Create flip/reverse counterfactual videos and score pair accuracy”: CRPO/DyBench (2605.21988).
- “Audit timestamps versus visual order”: temporal channel-use decomposition (2607.12304) includes independent pixel/timestamp/RoPE interventions and spacing warps.
- “Generate simple videos with exact event counts”: Low-Frequency Trap (2608.06361) already provides traces, frequency/count sweeps and evidence interventions.
- “Measure abstention when video sampling misses evidence”: VirtueBench; physical unanswerability: TRAPSBench.
- “Check cross-image geometric correspondence or triplet consistency”: SOCO (2605.31597) and CoRe (2607.12786).
- “Use spatial equivariance for GUI grounding”: ReGUIDE (2505.15259).
- “Benchmark updating stale visual memory”: WorldMemArena and MemLens.

## Audit method and practical constraints

Search used primary arXiv pages/HTML and official proceedings/project pages, with third-party pages only as discovery pointers. All 18 detailed sources have first submission dates before the stated cutoff, retrieved from arXiv citation metadata. Most are preprints; do not imply peer review for all. Date corrections from primary metadata supersede search-result dates: Task-State Representation is 2026-07-01, TRAPSBench 2026-08-13, IRA 2026-07-28. No code was run to reproduce their reported numbers, and source/checkpoint availability has not been fully audited.

For compute forecasts, count total calls × measured mean seconds/call / 3600, then add at least 30% allowance for retries and final repeats. Report each model's resolution, frames, output cap, precision and GPU, since parameter count alone does not determine cost. Cache inputs and completed outputs, use short JSON choices, run models sequentially, and avoid online rollouts longer than two verification steps for the core project. A strong course result can be a clearly documented negative result or replication plus a controlled counterexample; publication is contingent on a nontrivial pilot and external validation.
